# Автоматическое добавление узлов IONOS Cloud

Реализована цепочка **IONOS Cloud / Data Center Designer (Cloud API v6)** → Debian → Xray Reality/Vision → TLS-шлюз с подписью устройства → серверная региональная политика → проверка → существующий пул приложения.

Это **не API обычного VPS+** и не старый Cloud Panel API v1. Уже работающие узлы других провайдеров, Android, активация и ключи доступа не изменяются. Само развёртывание этой ветки не покупает серверы: оба переключателя закупки по умолчанию выключены, бюджет равен нулю.

## Как работает

1. Существующий планировщик ёмкости определяет, нужен ли ещё один узел. Используется прежний учёт устройств и свободных мест, а не клиентская команда «купить сервер».
2. До записи заказа проверяются настройки, бюджет, лимиты и обязательные защиты. Профиль региона задаёт конкретные CPU/RAM/диск/образ, а не автоматически выбранный тариф.
3. В БД создаётся `ionos_provision_jobs`: уникальная операция и SSH-ключи только этого узла. Общая аренда блокировки сериализует создание ресурсов между регионами и процессами.
4. Создаются отдельный виртуальный дата-центр, публичная LAN и VM с загрузочным SSD, cloud-init и firewall. Никакие существующие дата-центры/VM не переиспользуются и не удаляются.
5. Создаётся уникальная A-запись в заранее делегированной зоне IONOS Cloud DNS. По SSH с заранее известным ключом хоста загружается установщик; он запускается асинхронно через systemd.
6. **На VPN-узле** устанавливаются проверенный по SHA-256 выпуск Xray, firewall, доверенный TLS-сертификат и шлюз устройств. Списки региональных ограничений готовятся там же; затем обновляются серверным таймером. Клиент ничего из этого не скачивает при подключении.
7. Проверяются политика, доступ узла к API авторизации и отказ неподписанному устройству. Контроллер независимо проверяет TLS/имя/SPKI, provider firewall, установку отдельного временного UUID и реальный HTTPS-трафик через оба Xray-процесса. Временный UUID удаляется в `finally`.
8. Только после всех проверок узел получает `active/healthy` и становится доступен в существующем каталоге приложения. Неуспешный или ещё готовящийся узел туда не попадает.

### Защита от повторного списания

Каждый создающий Cloud POST сначала записывается в журнал. Если ответ потерян, контроллер ищет ресурс по уникальному имени операции. Он **не повторяет неизвестно чем завершившийся POST**. Если ресурс так и не найден, операция остаётся на проверку оператору. DNS использует документированный PUT с постоянным UUID записи.

База данных вместе с журналом и SSH-ключами должна иметь закрытый доступ и резервное копирование. Не очищайте журнал, не удаляйте строки вручную и не запускайте две независимые копии контроллера с разными БД на одном контракте. Откат миграции с непустым журналом специально запрещён.

## Что один раз подключить перед реальным запуском

Выполняется на **управляющем Linux-сервере**, не в Android Studio. API-токены не надо присылать в переписку или коммитить.

| Настройка | Требование |
| --- | --- |
| `IONOS_CLOUD_TOKEN`, `IONOS_CLOUD_CONTRACT_NUMBER` | Токен выбранного Cloud-контракта с необходимыми правами создания ресурсов; не токен сайта/бота |
| `IONOS_CLOUD_REGION_PROFILES_JSON` | Явный профиль для каждого используемого кода региона; публичный cloud-init Debian amd64, конкретный UUID образа |
| `IONOS_CLOUD_MANAGEMENT_IPV4` | Публичный исходящий IPv4 управляющего сервера; SSH разрешён только с него |
| `IONOS_CLOUD_DNS_ZONE_ID`, `IONOS_CLOUD_DOMAIN_SUFFIX` | Включённая **Cloud DNS** зона, делегированная на IONOS; например отдельная зона `vpn.your-domain.tld` |
| `IONOS_CLOUD_DNS_TOKEN` | Отдельный токен для этой DNS-зоны или пусто для использования Cloud-токена |
| `IONOS_CLOUD_GATE_AUTHORIZE_URL` | Действующий доверенный HTTPS-адрес `/internal/device-gate/authorize`, доступный с VPN-узлов |
| `IONOS_CLOUD_GATE_AUTHORIZE_KEY` | Тот же отдельный шлюзовой секрет, что `DEVICE_GATE_API_KEY` **на API авторизации**; 32–256 URL-safe символов |
| `IONOS_CLOUD_ACME_EMAIL`, `IONOS_CLOUD_ACME_TERMS_ACCEPTED` | Почта оператора и явное принятие условий ACME/Let's Encrypt оператором |
| `IONOS_CLOUD_XRAY_VERSION`, `IONOS_CLOUD_XRAY_SHA256` | Зафиксированный совместимый выпуск Xray и проверенный SHA-256 **архива `Xray-linux-64.zip`**, не отдельного бинарника |
| Стоимость, бюджет, лимиты | `AUTO_PROVISION_SERVER_MONTHLY_COST_EUR`, `AUTO_PROVISION_MONTHLY_BUDGET_EUR`, почасовой/суточный предел |

Контроллер не регистрирует новый аккаунт, не добавляет платёжную карту, не покупает домен и не меняет DNS-делегацию корневого домена. Эти первоначальные настройки аккаунта выполняет владелец. Отдельную подзону нужно делегировать один раз; дальше A-записи создаются автоматически.

Адрес API авторизации уже должен быть настроен владельцем. Если он сейчас доступен только через SSH-туннель/loopback, необходимо сначала предоставить нужный HTTPS-маршрут, сохранив проверку `X-Device-Gate-Key`. Установщик не раскрывает внутренний backend и не меняет firewall управляющего сервера. Развёрнутые backend и API авторизации должны поддерживать существующий протокол региональной политики v2 из базовой ветки.

### Настройка и проверка без покупки

Разверните backend этой ветки целиком, включая каталог `deploy/` рядом с `src/`, в отдельном тестовом релизе. Не используйте старые разовые скрипты из `deploy/device-gate/` с зашитыми адресами/номерами узлов для этой установки. Сделайте штатную резервную копию БД и примените миграцию:

```bash
python -m alembic upgrade head
python -m src.backend.ionos_cloud status
```

В закрытом окружении backend задайте `AUTO_PROVISION_PROVIDER=ionos_cloud`, но оставьте `AUTO_PROVISION_ENABLED=false` и `IONOS_CLOUD_APPLY_ENABLED=false`. Список подходящих образов можно получить **без создания ресурсов**:

```bash
python -m src.backend.ionos_cloud images --location de/fra
```

Пример структуры профиля, **UUID необходимо заменить выбранным из своего Cloud-каталога**:

```dotenv
IONOS_CLOUD_REGION_PROFILES_JSON={"de":{"location":"de/fra","image_id":"REPLACE_WITH_IMAGE_UUID","server_type":"VCPU","cores":2,"ram_mb":4096,"disk_gb":20}}
```

Заполните остальные параметры из таблицы и существующие настройки безопасности:
`POOL_ACCOUNTING_BRIDGE_ENABLED`, `POOL_BRIDGE_API_KEY`, `UNIQUE_DEVICE_CREDENTIALS_ENABLED`, `PER_DEVICE_RATE_LIMIT_ENFORCED`, `SMTP_ABUSE_PROTECTION_ENABLED`, `DEVICE_BOUND_GATE_ENABLED`.
Сохраните прежние `XRAY_CONFIG_PATH=/usr/local/etc/xray/config.json`, `DEVICE_GATE_SERVICE_NAME=emery-device-gate`, `RECOVERY_SSH_USER=root`; внешний `XRAY_CREDENTIAL_SCRIPT` для этого адаптера не используется.

```bash
python -m src.backend.ionos_cloud plan --region de
python -m src.backend.ionos_cloud preflight --region de
```

`plan` проверяет локальную конфигурацию/ограничители. `preflight` читает свойства образа и DNS-зоны через API. Ни одна команда ничего не покупает. Их успех **не заменяет** испытание реального узла: SSH, DNS-делегация, ACME, установка пакетов и маршрутизация проверяются уже при подготовке VM.

## Включение после проверки настроек владельцем

Разрешать оба `AUTO_PROVISION_ENABLED=true` и `IONOS_CLOUD_APPLY_ENABLED=true` можно **только когда готовы разрешить платные ресурсы**. Бюджет и оценка стоимости должны быть положительными. Ноль означает запрет, не безлимит. IONOS Cloud оплачивается по потреблению; оценка в guardrail не является лимитом биллинга IONOS и должна учитывать VM, SSD, IP, трафик и налоги.

Для первого узла оставьте оба переключателя **выключенными в окружении работающего backend**. Разрешите их только для отдельного запуска CLI, чтобы фоновый планировщик ещё не создавал узлы:

```bash
AUTO_PROVISION_ENABLED=true IONOS_CLOUD_APPLY_ENABLED=true python -m src.backend.ionos_cloud scale-once --allow-paid
python -m src.backend.ionos_cloud status
```

Во время первого испытания оператор продолжает **тот же `node_id`**:

```bash
AUTO_PROVISION_ENABLED=true IONOS_CLOUD_APPLY_ENABLED=true python -m src.backend.ionos_cloud advance --node-id NODE_ID --allow-paid
```

`NODE_ID` заменяется числом из `status`. Не создавайте новый draft вместо временно зависшего. Во время первого испытания проверьте живым приложением подключение в обоих режимах политики, ограничения, лимит скорости, перезагрузку VM и отказ другому/отозванному устройству. Только затем включите оба переключателя в окружении backend и перезапустите его штатным способом: дальнейшие итерации будет выполнять существующий планировщик ёмкости.

## Сбои, обновления и отключение

- `ionos_post_outcome_unknown_reconciling`: только сверка в DCD по `operation_id`/имени; не удалять намерение и не повторять заказ вручную без проверки наличия ресурса.
- `ionos_bootstrap_failed`: узел остаётся вне пула. После устранения причины на **этом же узле** `systemctl restart emery-ionos-bootstrap.service` продолжает сохранённые этапы. Доступ только штатным SSH с проверкой ключа хоста; `StrictHostKeyChecking=no` не нужен.
- В `/var/lib/emery-ionos/operation.json` записаны завершённые этапы; `error.json` и журнал systemd содержат только безопасные коды ошибок. Приватные файлы `config.json`, `seed.json`, ключи и environment-файлы нельзя публиковать.
- Конфигурация и хеш установочного комплекта фиксируются для операции. Не меняйте образ, регион, контракт или установщик на середине заказа. При несовпадении работа останавливается для проверки оператором.
- Если ожидание превысило установленный срок, требуется проверка оператором. Автоматического удаления, подмены VM или бесконечных новых заказов нет.
- Сертификат обновляется certbot-таймером с сохранением ключа/SPKI; неожиданная смена ключа останавливает шлюз. Перед штатной ротацией ключа нужен отдельный согласованный процесс обновления pins устройств.
- Серверная региональная база обновляется своим таймером; при устаревшей базе региональный режим закрывается по прежней логике. **Полнота стороннего набора не является гарантией юридической полноты реестра.** Источник правил в этой задаче не менялся.
- Firewall и лимиты устройств восстанавливаются после перезагрузки. Снаружи доступны только шлюз 24443 и HTTP 80 для ACME; SSH 22 — только управляющему IPv4. VLESS/UUID-порты остаются на loopback.
- `AUTO_PROVISION_ENABLED=false` + `IONOS_CLOUD_APPLY_ENABLED=false` прекращают новые операции. Работающие VPN-узлы сохраняются. **Отключение автоматики не прекращает оплату уже созданных ресурсов у IONOS.**

## Проверки в коде и первичные спецификации

Тесты не используют действующие Cloud-токены и не создают ресурсы:

```bash
python -m pytest -q
python tests/test_ionos_bootstrap_node.py
```

Контракты API сверены с [официальным Cloud SDK](https://github.com/ionos-cloud/sdk-python/tree/master/docs), [Cloud DNS SDK](https://github.com/ionos-cloud/sdk-python-dns/blob/master/docs/api/RecordsApi.md) и [примером DNS record официального Terraform provider](https://github.com/ionos-cloud/terraform-provider-ionoscloud/blob/master/docs/resources/dns_record.md). Поведение продления ключа описано в [руководстве Certbot](https://eff-certbot.readthedocs.io/en/stable/using.html#renewing-certificates).
