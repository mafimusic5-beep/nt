# Ручная покупка VPS — автоматическая настройка

Этот режим не требует DCD, API-токена IONOS, Cloud DNS или доступа к оплате. Владелец покупает VPS сам. Управляющий backend устанавливает VPN по SSH, проверяет его и только после успешной проверки допускает узел в рабочий пул приложения.

**APK пересобирать не требуется.** Ядро, интерфейс и протокол активации приложения не изменены. Используется существующий установщик Xray Reality/Vision, шлюз с подписью устройства и серверная региональная политика. Источники региональных списков не менялись.

## Что подготовить

| Где | Что требуется |
| --- | --- |
| Управляющий Linux-сервер | Работающий backend этой ветки, его прежняя БД, доступ к API авторизации и исходящий постоянный публичный IPv4 |
| Новый VPS | Чистый Debian 12/13, amd64, systemd, Python 3, OpenSSH и `ss`; публичный IPv4; SSH на порту 22 |
| SSH | Отдельный Ed25519-ключ входа для этого VPS; его публичная часть уже установлена для root; проверенный публичный ключ самого SSH-сервера |
| DNS | Отдельное нейтральное имя, например `edge-frankfurt-01.neutral.example`; A-запись прямо на IPv4 VPS, без CDN-прокси и без AAAA-записи. Домен не используется сайтом, ботом или API бренда |
| Firewall провайдера | Входящий TCP 22 только от управляющего IPv4; TCP 80 и 24443 из интернета; исходящие DNS и HTTPS разрешены |

DNS и внешний firewall задаются владельцем в обычном кабинете. Установщик проверяет доступность, но не меняет настройки кабинета: именно поэтому ему не нужен токен провайдера. Локальный firewall, TLS-сертификат, VPN и службы на самом VPS настраиваются автоматически. Безлимитный трафик и цена определяются приобретённым тарифом, не этим кодом.

ASN и публичный IP **не скрываются** — это невозможно, пока сервер принимает соединения на этом IP. Защита ниже убирает прямую публичную привязку IP к продукту и владельцу: имя и сертификат нейтральны, PTR проверяется, неправильный или отсутствующий SNI отклоняется, HTTP/HTTPS-сайт на VPN-IP не поднимается, а TCP 80 открывается локальным firewall только на время ACME-выдачи/продления сертификата. Провайдер и владелец аккаунта всё равно знают арендатора; авторизованный пользователь приложения также может увидеть IP подключённого узла. Это не средство скрыться от законного запроса и не обещание неотслеживаемости.

Нельзя использовать сервер с действующим сайтом, ботом, другим VPN или контейнерами. Проверка таких следов блокирует установку; опции принудительного затирания нет. Управляющий сервер и API авторизации нельзя выбрать в качестве VPN-узла.

## 1. Один раз: подготовить управляющий backend

Все команды ниже выполняются **на управляющем Linux-сервере**, из каталога backend, где находятся `src/`, `deploy/` и `alembic.ini`. Это не PowerShell Android Studio. Используйте Python из виртуального окружения backend и того же системного пользователя, от которого работает backend. В поставляемом примере systemd это пользователь `emery`; существующую установку на другого пользователя не переводите.

Разверните всю backend-часть ветки в отдельном тестовом релизе. Не меняйте Android и не заменяйте действующую базу пустой. Сделайте штатную резервную копию БД, затем:

```bash
python -m alembic upgrade head
```

Добавляется только таблица журнала `manual_vps_setup_jobs`. При включении режима backend запускает отдельного фонового работника; установка не задерживает обычные проверки VPN, обслуживание подключений и задания по активации.

Сохраните закрытую копию `deploy/manual-vps/profile.example.json` как `/etc/emery/manual-vps/profile.json`. Каталог должен принадлежать пользователю backend с правами `700`, файл — с правами `600`. Аналогичные права нужны для файлов конкретных узлов и приватных SSH-ключей. Файлы не должны быть симлинками.

Заполните профиль:

- `management_ipv4`: фактический исходящий IPv4 управляющего сервера. Он сравнивается с источником SSH-соединения до установки firewall.
- `authorize_url`: существующий HTTPS-адрес API авторизации с путём `/internal/device-gate/authorize`. Не публичный адрес сайта и не токен бота.
- `acme_email`: почта владельца; `acme_terms_accepted=true` только после принятия владельцем условий Let's Encrypt. HTTP 80 требуется для выдачи и продления сертификата.
- `xray_version` и `xray_sha256`: зафиксированный совместимый выпуск Xray и SHA-256 его архива `Xray-linux-64.zip`. Не `latest`, не хеш отдельного исполняемого файла.
- `reality_server_name`: выбранное совместимое имя Reality; `probe_url`: HTTPS-ресурс для проверки реального трафика, доступный в обоих режимах политики.
- `bootstrap_timeout_seconds`: 3600–14400 секунд, по умолчанию в примере 7200.
- `brand_domains`: все базовые домены сайта, API и других сервисов бренда. Публичное имя VPN не может быть их поддоменом.
- `forbidden_public_markers`: собственное название продукта/компании строчными латинскими буквами и цифрами. Встроенно также запрещены `skryon`, `emery`, `vpn`, `xray`, `vless`, `proxy`, `tunnel`, `openvpn` и `wireguard`.
- `separate_service_hosts`: точные DNS-имена сайта и API, которые обязаны указывать не на VPN-IP. Хост из `authorize_url` должен присутствовать в списке и относиться к одному из `brand_domains`. Если бот имеет свой webhook-хост, добавьте и его; Telegram-бот без публичного webhook-хоста добавлять некуда.

Для нейтрального домена включите приватность WHOIS у регистратора и не используйте в публичном имени название продукта, `vpn`, `proxy` или похожие слова. PTR в панели VPS оставьте провайдерским либо задайте нейтральным; PTR с маркером бренда заблокирует публикацию узла. Сертификат публикуется в Certificate Transparency, поэтому брендовый домен здесь использовать нельзя. Почта ACME в TLS-сертификат не попадает, но должна принадлежать владельцу и храниться только в закрытом профиле.

В **существующее** закрытое окружение backend добавьте настройки, сохранив остальные действующие параметры и секреты:

```dotenv
AUTO_PROVISION_ENABLED=false
IONOS_CLOUD_APPLY_ENABLED=false
MANUAL_VPS_SETUP_ENABLED=true
MANUAL_VPS_PROFILE_PATH=/etc/emery/manual-vps/profile.json
MANUAL_VPS_GATE_AUTHORIZE_KEY=REPLACE_LOCALLY_WITH_EXISTING_DEVICE_GATE_API_KEY
```

`MANUAL_VPS_GATE_AUTHORIZE_KEY` должен совпадать с отдельным `DEVICE_GATE_API_KEY` на API авторизации. Не присылайте его в чат, не храните в GitHub и не включайте в APK. Токен IONOS, номер Cloud-контракта, Cloud DNS и бюджет автозакупки этому режиму не нужны. Если включён хотя бы один переключатель покупки, установка блокируется. При включённом ручном режиме планировщик автозакупки также блокирует создание платных ресурсов.

Сохраняются обязательные защиты: `POOL_ACCOUNTING_BRIDGE_ENABLED`, `POOL_BRIDGE_API_KEY`, `UNIQUE_DEVICE_CREDENTIALS_ENABLED`, `PER_DEVICE_RATE_LIMIT_ENFORCED`, `SMTP_ABUSE_PROTECTION_ENABLED`, `DEVICE_BOUND_GATE_ENABLED`. Эти настройки должны уже быть согласованы с работающим API. `RECOVERY_SSH_USER=root`, `RECOVERY_ALLOW_UNKNOWN_HOST_KEYS=false`; используется встроенный SSH-транспорт, без внешнего `XRAY_CREDENTIAL_SCRIPT`.

После проверки окружения перезапустите только backend штатным способом. Отсутствующий секрет или небезопасная конфигурация блокируют настройку нового VPS, а не открывают доступ без авторизации.

## 2. Каждый новый VPS: купить и зарегистрировать

Купите чистый сервер вручную, установите его публичный SSH-ключ входа через штатную панель/консоль и настройте A-запись с внешним firewall. Каждый VPS получает отдельный ключ входа. Приватная часть хранится только у управляющего backend.

Публичный SSH-ключ **самого сервера** получите через доверенную консоль провайдера из `/etc/ssh/ssh_host_ed25519_key.pub`. Это файл с окончанием `.pub`, не приватный ключ. Он нужен для проверки, что управляющий сервер подключается к выбранному VPS. Автоматического доверия неизвестному ключу или отключения проверки SSH нет.

Сохраните закрытую копию `deploy/manual-vps/node.example.json`, например как `/etc/emery/manual-vps/frankfurt-01.json`, и заполните IP, DNS-имя, регион, отображаемое название, путь к приватному ключу и проверенный публичный ключ SSH-сервера. Значения ёмкости и полосы пропускания выбирает владелец по своему тарифу и нагрузочным испытаниям; числа в примере не гарантируют производительность любого VPS.

Сначала проверка без изменений:

```bash
python -m src.backend.manual_vps check --node-file /etc/emery/manual-vps/frankfurt-01.json
```

Она не пишет в БД, не устанавливает пакеты и не меняет SSH/DNS/firewall. При успешной проверке можно разрешить установку **именно на этом новом VPS**:

```bash
python -m src.backend.manual_vps setup --node-file /etc/emery/manual-vps/frankfurt-01.json --apply --wait
```

Без `--wait` команда только регистрирует проверенный VPS; фоновый работник запущенного backend продолжит настройку. С `--wait` CLI также продолжает тот же журнал, показывает этапы и ждёт результата. Нажатие Ctrl+C не удаляет VPS, не останавливает его установщик и не очищает журнал.

Автоматически выполняются проверка чистого сервера, фиксация владельца установки, отключение парольного SSH-входа, установка проверенного архива Xray, локальный firewall, доверенный TLS-сертификат, шлюз устройств, серверная региональная политика и проверки работоспособности. Приватный SSH-ключ хоста и существующие `authorized_keys` не заменяются. Списки доменов бренда и маркеры остаются на управляющем backend и не копируются в конфигурацию VPS.

Настройка может занять несколько минут: пакеты, сертификат и региональные данные готовятся на новом VPS. Уже работающие серверы и подключение пользователей этой установки не ожидают. Дубликат того же задания не создаёт второй узел и не переустанавливает готовый VPN.

## 3. Статус и сбои

```bash
python -m src.backend.manual_vps status
```

Этапы: `preflight` → `bootstrap` → `bootstrapping` → `verify` → `ready`. Только `ready` после проверки реального HTTPS-трафика через оба VPN-режима, TLS/SPKI, отказа неподписанному устройству, удаления проверочного UUID и внешней проверки DNS/PTR/SAN/SNI/портов открывает узел для подключений. На стадии подготовки сервер не принимает пользовательские назначения. При обнаружении брендового имени, дополнительного SAN, ответа без правильного SNI либо открытых TCP 80/443 узел остаётся заблокированным.

Ошибки останавливают конкретное задание для проверки владельцем, не запускают покупку замены. После устранения причины повторите **тот же node_id**:

```bash
python -m src.backend.manual_vps resume --node-id 42 --apply --retry --wait
```

Замените `42` числом из `status`. Явный `--retry` снимает паузу и обновляет срок ожидания, но не разрешает изменённый IP, SSH-ключ, установочный комплект или профиль. Другой узел вместо зависшего автоматически не создаётся. Если удалённый `emery-ionos-bootstrap.service` перешёл в `failed`, после изучения безопасного кода ошибки и исправления причины владелец должен штатно перезапустить эту службу **на том же VPS**. Она продолжит свои сохранённые этапы.

Журнал установки на VPS использует существующие пути `/var/lib/emery-ionos` и службу `emery-ionos-bootstrap.service`; это повторно используемый установщик, не подключение к Cloud API. Отдельный маркер `/var/lib/emery-manual-vps/owner.json` не позволяет другой операции перехватить этот сервер. Не удаляйте маркеры или строки БД для обхода проверки.

Для остановки дальнейшей настройки задайте `MANUAL_VPS_SETUP_ENABLED=false` и штатно перезапустите backend. Готовые VPN-узлы сохраняются. Уже запущенный установщик на VPS продолжает работу независимо; его остановка при необходимости — отдельное действие владельца. Оплата, продление, удаление и внешний firewall остаются в кабинете владельца: этот режим ими не управляет.

## Проверки перед выпуском

Тесты используют временную БД и имитацию SSH; они не покупают и не настраивают настоящие серверы:

```bash
python -m pytest -q
```

Перед выпуском владельцу нужен отдельный живой тест на чистом VPS: установка, оба режима региональной политики, вход разрешённого устройства, отказ чужому/отозванному устройству, лимит скорости и восстановление после перезагрузки. Успех модульных тестов сам по себе не подтверждает сетевую доступность конкретного VPS, DNS и внешнего firewall.
